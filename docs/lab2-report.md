## 2. Аргументація архітектурних рішень (схема підключення)

Повна таблиця «пін → функція → пристрій» з джерелами — `docs/pinout.md` §1; бюджет живлення §3; параметри шин §4; відхилені варіанти §6.

* **Чому MPU-6050 на I²C1 (PB8/PB9):** єдина пара апаратного I²C на Arduino-роз'ємах без конфліктів; модуль GY-521 має свої pull-up.
* **Чому камера на окремому програмному SCCB (PB10/PB4), а не на I²C1:** SCCB ≠ I²C (9-й біт «don't care», немає repeated-START), HAL трактує
  NACK як помилку й залишає блок у BUSY; PB10 (I2C2_SCL) і PB4 (I2C3_SDA) — піни різних блоків, апаратною шиною не стають. Bit-bang ізолює збій камери від MPU.
* **Чому XCLK = MCO1 з HSI 16 МГц:** діапазон камери 10–48 МГц, HSI дає чистий сигнал; PLL-джерело давало «сміття» в довідковому проєкті.
* **Чому SPI2 і програмний CS (PB12):** SPI1 конфліктує з LED (PA5) і PWM (PA6/PA7); програмний CS тримає опущеним CS# на всю транзакцію «команда + дані».
* **Чому SPI mode 0 і ≈390 кГц, I²C 100 кГц:** standard mode (було 50 кГц для довгих дротів, проблема 2 ЛР1; після виправлення читання — проблема 6 — стабільно на 100 кГц); розрахунок із дерева тактування — `docs/pinout.md` §4.
* **Чому серво від окремого 5 В:** пікові ≈ 650 мА на серво ≫ запас LDO 3.3 В і ліміт USB; спільний GND потрібен як опорний рівень PWM.
* **Конфлікт камери з іншими інтерфейсами:** паралельна шина (11 ліній) резервується на PC0–PC7 + 3 піни керування; жоден із них не перетинається з I2C1/SPI2/TIM3/ADC (`docs/pinout.md` §1.1). Не змонтовано в ЛР2.

## 4. Самоперевірка (п. 4.2)

Формат (придатний для автоматичного розбору): `[st] <NAME> <PASS|FAIL> key=value …`, підсумок `[st] RESULT pass=N total=M`.

| Пристрій | Ідентифікація | Мін. ініціалізація | Перевірка правдоподібності |
|----------|---------------|---------------------|-----------------------------|
| MPU-6050 | WHO_AM_I = 0x68 | PWR_MGMT_1 = 0 (вихід зі sleep) | \|a\| = 1 g ± 15 % у спокої (zero-g offset + допуск чутливості); T кристала 15…40 °C |
| OV7670 | PID = 0x76, VER = 0x73 | XCLK 16 МГц (MCO1) | повторне читання при збої; відновлення шини |
| W25Q64 | JEDEC = EF 40 17 | Release Power-down | стирання сектора 0x7FF000, запис 16 байт, побайтне порівняння |
| GM5528 ×4 | — | ADC1, 84 цикли | значення не «прилипли» до 0/4095; мВ = raw·3300/4095 |
| Серво ×2 | — | TIM3 50 Гц | ширина імпульсу (CCR) = задана; фізично — аналізатором (§5) |

Лог із плати (2026-10-20, F411, серво вимкнені):

```
[st] BEGIN
[st] I2C_SCAN  n=1 addrs= 0x68
[st] MPU6050  PASS who=0x68 ax=-1828 ay=-12592 az=-8928 mag_mg=947 temp_cC=2350 tries=1
[st] OV7670   PASS rc=0 pid=0x76 ver=0x73
[st] W25Q_ID  PASS rc=0 jedec=EF4017
[st] W25Q_RW  PASS rc=0 addr=0x7FF000 bytes=16 first=0xA0
[st] ADC_TL   PASS raw=2567 mv=2068
[st] ADC_TR   PASS raw=2843 mv=2291
[st] ADC_BL   PASS raw=2197 mv=1770
[st] ADC_BR   PASS raw=2366 mv=1906
[st] RESULT pass=8 total=8
```

MPU-6050 відповідає не завжди: після перестановок проводів на макетці бувало 3 з 8, при надійному контакті 8 з 8 (проблема 6).

## 5. Записи логічного аналізатора

Записи — `docs/captures/` (`.sr`, `.pvs`, декодований `.txt`, скріншоти). Канали, частоти, декодування, порівняння з datasheet, виміри, ручне
декодування і аномалії — `docs/analysis.md`.

| Інтерфейс | Запис | Що видно |
|-----------|-------|----------|
| I²C (MPU-6050) | `i2c_mpu6050_whoami_burst` | WHO_AM_I = 0x68, burst 6 байтів з 0x3B |
| SCCB (OV7670) | `sccb_ov7670_pid` | PID 0x76, VER 0x73, між записом і читанням STOP |
| SPI (W25Q64) | `spi_w25q64_jedec_write` | JEDEC `EF 40 17`; `06` → `20` → `06` → `02` → `03` |
| UART | `uart_stlink_log_tick` | текст `tick …`, 115200 8N1 |
| PWM | `pwm_servo_az_1000_2000` | 1000 / 1500 / 2000 мкс, період 19,8 мс |
| ADC | `adc_marker_pa5` | маркер PA5 150 мкс навколо вимірювання |
| Аномалія | `i2c_nack_addr0x69` | NACK по адресу 0x69 |

Аномалії: навмисний NACK; сміття на MOSI при читанні SPI (розбіжність HAL і шини, виправлено в `platform_buses.c`).

## 7. Тестування

Команда `make test` (Docker, gcc, без плати), `make coverage` — з порогом **90 %** рядків для Devices/ і App/quadrant (поріг обрано так, щоб ловити «забуті» гілки обробки помилок,
але не вимагати штучного покриття glue-коду).

* Каркас: власний на `assert`-логіці (`tests/test.h`); Unity/CMock не брали, бо немає потреби в генерації моків для 3 драйверів. Чого це позбавляє: автоматичних моків, багатих ASSERT-макросів, ізоляції тестів.
* Test doubles: **fake** `fake_i2c` (пам'ять регістрів + інʼєкція NACK + журнал транзакцій), **fake** `fake_w25q` (модель команд 0x06/0x05/0x9F/0x20/0x02/0x03: WEL, BUSY, AND-семантика програмування, загортання в межах сторінки), **mock** `mock_sccb` (перевіряє взаємодію: скільки разів читали, скільки пауз, що записано в COM7). Mock потрібен там, де цікавить саме *поведінка* виклику (повтори/паузи), а не стан пристрою.
* Покрито: перетворення сирих даних (accel→мг, температура за формулою datasheet, |a|, raw→мВ, кут→мкс); помилки шини (NACK, timeout, неочікуваний ID: 0xFF/0x00/інший); послідовність команд до SPI-flash (WE перед **кожною** сторінкою, перевірка WEL, не перетинати межу сторінки, wait-ready з таймаутом).
* Вектори: JEDEC `EF 40 17`, PID/VER `76 73`, WHO_AM_I `0x68` — значення з UART-логу реального заліза (`tests/vectors/vectors.h`). Burst-байти MPU (`1E 1C D0 C0 E2 A8`) взяті із запису `.sr`.
* Datasheet-приклад: температура MPU `T = raw/340 + 36.53`.
* Результат останнього прогону: **136 перевірок, 0 помилок; покриття рядків: mpu6050 100 %, w25q 100 %, ov7670 100 %, quadrant 100 %.**
* Свідомо не покриваємо: `Platform/` і `Core/` (код поверх HAL — тестується лише на залізі), `App/selftest.c`, `cli.c`, `app.c` (I/O-склейка; перевіряється самоперевіркою на платі).
* Знайдені тестами дефекти: ☐ ⟦на момент написання тести не виявили дефектів у драйверах; єдиний збій прогону — помилка в очікуванні самого тесту (998 vs 999 мг), виправлено⟧. Дефект, знайдений на залізі й закритий тестом: проблема 5 (повторне читання при неправильному ID).
* CI: `.github/workflows/ci.yml` — `make coverage`, `check_deps.py`, збірка F411/F446 на кожен PR.
